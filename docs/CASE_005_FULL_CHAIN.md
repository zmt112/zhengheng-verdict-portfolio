# CASE-005：从行程到判责的完整可操作链路

## 1. 为什么选这个案件

案件名为“截图真实，但不能证明司机取消时未到达”。它不是为了证明 OCR、ASR 或图片反作弊有多强，而是验证一个更关键的产品能力：媒体材料通过真实性审核后，系统仍需判断它能证明哪个时刻、哪个事实，不能把“材料是真的”直接等同于“用户主张成立”。

本案同时产生两个不同结果：责任规则支持司机已经履约；体验侧发现司乘位于不同入口，需要进入上车点治理。责任判定和体验问题被分流，而不是强行压成一个“谁对谁错”。

完整机器可读 fixture 位于 `fixtures/case-005/full-chain.json`。

## 2. 案件故事

2026 年 7 月 18 日 14:18，乘客发起一笔快车演示订单。平台上车点锚点为 `116.465063, 39.999538`，演示规则中的有效范围为 60 米。司机从 `116.481499, 39.990475` 接驾。

14:29:45，乘客在 App 中截屏。当时司机距上车点约 187 米，因此截图本身是真实的。14:31:06，司机进入有效范围；14:31:12 点击到达，并停在距锚点 28 米的位置。乘客当时位于另一个入口，距平台锚点约 129 米。14:32:10 双方通过平台电话联系 28 秒，但仍未碰面。14:37:34，司机在到达点击 382 秒后以“乘客未出现”取消，订单产生 8 元演示取消费。

乘客随后发起纠纷：“司机一直没到我这里，却收了取消费。截图和录音都能证明。”她上传了 14:29 的地图截图和平台通话录音。

## 3. 从端到端发生了什么

### 3.1 行程侧产生第一方事件

订单服务产生发单、接单、到达点击和取消事件；定位 SDK 产生司机轨迹、定位精度和进入围栏事件；导航服务保存路线版本；通信服务保存拨打、接通和时长；IM 服务保存双方消息。这些数据在纠纷发生前已经存在，因此属于第一方平台证据。

### 3.2 乘客侧提交纠纷和附件

乘客选择“司机未到上车点”并填写描述，上传地图截图和录音。客户端先申请上传凭证，附件写入对象存储，系统计算哈希并登记文件来源、拍摄或录制时间、上传时间、媒体类型和处理状态。

### 3.3 智能审核处理单份媒体

图片审核识别这是截图、未发现明显篡改，并通过 OCR 提取“14:29”和“距上车点约 190 米”。音频审核检查基础完整性，ASR 将通话转成带说话人的文本。

智能审核在这里完成的是“这份媒体是什么、是否完整、是否疑似作弊、里面有什么”，它不回答“司机最终有没有履约”。

### 3.4 证衡进行案件级证据编排

证衡将截图时间与平台轨迹对齐，发现截图发生在司机实际到达前 81 秒。截图证明的是 14:29:45 的位置状态，不能反驳 14:31 后司机已经到达的事实。录音和乘客定位则共同说明双方位于不同入口，但录音内容本身不能替代 GPS 证明车辆位置。

### 3.5 充分度门控与双结果输出

司机进入围栏、停留足时、完成联系和取消时间四项必要事实均被第一方证据支持，因此案件可以进入确定性规则计算。判责结果支持司机履约；同时创建“上车点入口歧义”的体验治理任务。

如果删除连续轨迹、把定位质量降级，或者将截图时间改成取消时刻，案件必须重新进入证据不足或冲突状态。这些变异是 Harness 的必要用例。

## 4. 接口契约

建议采用异步处理，不设计一个同时上传、解析、判责的万能接口。

### 4.1 创建纠纷工单

`POST /api/v1/dispute-tickets`

```json
{
  "orderId": "ORD-20260718-140805-005",
  "submittedBy": "PASSENGER",
  "category": "DRIVER_NOT_AT_PICKUP",
  "statement": "司机一直没到我这里，却收了取消费。截图和录音都能证明。"
}
```

返回 `ticketId`、允许的附件类型、单文件大小限制和上传会话。

### 4.2 上传附件

`POST /api/v1/dispute-tickets/{ticketId}/attachments`

使用 `multipart/form-data` 上传图片或音频。接口返回 `attachmentId`、内容哈希、存储状态和 `PENDING_AUDIT`，不在上传请求中等待 OCR/ASR。

### 4.3 查询解析状态

`GET /api/v1/dispute-tickets/{ticketId}/attachments/{attachmentId}`

```json
{
  "attachmentId": "IMG-005",
  "status": "PARSED",
  "smartAudit": {
    "isScreenshot": true,
    "manipulationRisk": "LOW"
  },
  "derivedEvidence": {
    "parserVersion": "demo-parser-1.0",
    "visibleTime": "14:29",
    "visibleDistanceText": "距上车点约 190 米"
  }
}
```

### 4.4 生成案件快照

`POST /api/v1/dispute-tickets/{ticketId}/case-snapshots`

服务端冻结订单事件、轨迹、通信日志、上传附件及所有解析版本，返回不可变的 `caseSnapshotId`。判责必须针对快照运行，不能直接查询持续变化的在线数据。

### 4.5 运行证据编排和判责门控

`POST /api/v1/case-snapshots/{caseSnapshotId}/evaluations`

```json
{
  "proofTemplateId": "CANCEL-ARRIVAL",
  "proofTemplateVersion": "2026.07-demo"
}
```

返回 facts、evidence ledger、gate、outcome、规则版本和治理任务。接口必须幂等：相同快照和规则版本重复运行结果一致。

### 4.6 人工确认或升级

`POST /api/v1/evaluations/{evaluationId}/actions`

动作包括 `ACCEPT_SUGGESTION`、`ESCALATE_REVIEW`、`REQUEST_EVIDENCE`。任何真实费用、处罚或封禁仍走现有审批或处置接口，本项目不直接绕过它们。

## 5. 与现有智能审核的边界

| 能力 | 智能审核 | 证衡 |
|---|---|---|
| 单张图或单段音频是否完整、清晰、疑似篡改 | 主责 | 消费审核结果 |
| OCR、ASR、截图识别 | 主责或上游能力 | 将解析结果登记为派生证据 |
| 某份材料能证明哪个事实和时刻 | 不足 | 主责 |
| 多源证据时间对齐和冲突发现 | 非核心 | 主责 |
| 当前证据是否足够输出责任结论 | 非核心 | 主责 |
| 规则版本、逐句引用、安全拒判 | 非核心 | 主责 |
| 从无法判责或入口歧义反推治理任务 | 非核心 | 主责 |

如果最终 Demo 只是“上传截图—AI 识别—输出谁有责”，它与智能审核确实没有足够区别，也不建议继续。创新成立的前提是把智能审核作为证据准入的一层，而把案件级证明、充分度门控、冲突/未知处理和反事实验证做成核心。

## 6. 我对当前想法的质疑

1. **不要为了完整链路重做两个 C 端 App。** 比赛作品只需要一个可回放的行程模拟器，能够产生真实格式的端上事件；否则大量时间会耗在叫车、接驾和地图动效上，却没有增加判责能力。
2. **没有规则就没有“正确判责”。** 60 米围栏、360 秒等待、有效联系的定义目前都是演示规则。若无法获得真实或经业务确认的规则，项目只能证明机制可运行，不能宣称业务结论正确。
3. **坐标系错误会制造假冲突。** 高德通常使用 GCJ-02，而其他开源地图和服务常使用 WGS84。司机、乘客、围栏和底图必须记录坐标系与转换版本。
4. **截图真实性不是证明力。** 一张完全真实的截图也可能截在错误时间，或只能证明展示结果，不能证明平台原始状态。
5. **ASR 文本不能冒充原始证据。** 必须同时保留原音频、哈希、ASR 版本、说话人分离结果和时间戳；模型没有听清的字段应为 UNKNOWN。
6. **演示数据不能既当输入又当答案。** 需要由生成器先冻结真值，再由独立解析/判责代码盲跑；否则只是把预设结论展示出来。
7. **“令人信服”需要区分内外部视图。** 内部处置员可以查看完整轨迹和质量字段，用户侧只能展示符合隐私与安全要求的决定性摘要，不能把另一方精确位置或通话内容全部暴露出去。

## 7. 需要业务侧提供或确认的数据

### P0：决定项目能否成立

1. 一类真实纠纷的脱敏事件 Schema，而不是直接提供个人数据；
2. 真实判责规则：围栏定义、等待阈值、联系要求、取消主体与例外；
3. 司机轨迹字段：时间、经纬度、坐标系、精度、采样间隔、数据中断标记；
4. 订单事件字段：事件名、发生时间、上报时间、操作者、原因码和规则版本；
5. 当前客服/判责员需要查看的系统和实际操作步骤；
6. 智能审核返回结果的字段样例，尤其是截图、PS、拍屏、音频完整性和模型版本。

### P1：让 Demo 具有真实感

1. 一份脱敏的导航规划响应或允许使用的高德 Web 服务 Key，由环境变量接入，不粘贴到代码或聊天中；
2. 3—5 个脱敏历史案件，由两名业务人员分别给出事实标注和最终结论；
3. 通话元数据 Schema；若不能使用录音，只提供人工改写的对话脚本即可；
4. 工单分类、状态流转、升级条件和现有处置动作；
5. 允许展示给用户的裁决解释边界。

### 不需要提供

- 真实姓名、手机号、身份证号、车牌；
- 未脱敏的精确家庭或常用地址；
- 未获授权的原始录音；
- 任何生产密钥或账号口令。

## 8. 推荐实现顺序

1. 行程生成器产生订单、轨迹、通信和纠纷事件；
2. 建立 D1 案件/事件/证据元数据与 R2 附件存储；
3. 实现工单和附件接口，样例截图与合成录音可真实上传、播放、解析；
4. 将现有智能审核结果以标准接口接入证据账本；
5. 生成不可变案件快照，运行现有确定性充分度引擎；
6. 工作台增加“行程回放—工单接入—证据解析—事实判定—裁决书”链路；
7. 为附件缺失、截图时间错位、GPS 降质、坐标系错误和证据冲突补充 Harness。

这一顺序先证明链路可运行和结论可验证，再替换更真实的数据源或模型，不会因为暂时拿不到内部数据而停工。
