# 证衡工作台：竞品模式、界面重构与质量 Harness

## 1. 调研目标与边界

本轮调研不寻找可以直接复制的视觉稿，而是回答三个问题：

1. 成熟风险案件产品如何组织高密度信息；
2. 人机协作判责中，哪些动作必须由人工掌控；
3. 如何把“简洁、易用、可信”转化为可重复执行的代码闸门。

调研对象均选取官方产品页或官方文档，避免二手测评造成产品能力误读。

## 2. 市场产品的共性模式

| 产品 | 官方资料中的核心模式 | 对证衡的启发 | 不直接照搬的部分 |
|---|---|---|---|
| Stripe Radar Reviews | 审核队列进入单笔详情；展示风险洞察、相关交易与历史操作；支持分配、上一条/下一条和 J/K 快捷键 | 高频审核需要“队列—详情—动作”连续流，减少返回列表和页面跳转 | 支付交易字段、通过/退款等业务动作 |
| Persona Cases | 将 Configure、Investigate、Decide 串成案件流程；汇聚内外部数据；提供模板、分配、升级、权限和审计日志 | 案件应是证据与协作的单一事实源；规则和审计按需展开 | 通用 KYC 模板与组织权限模型 |
| Unit21 Case Management | AI 用于分流、补充信息和摘要；最终决定由人工掌控；保留完整审计链，支持队列和质检 | AI 负责整理，不越权替代责任规则；关键处置需要人类确认且全程可追溯 | AML/SAR 专业流程和图谱能力 |
| Sift | 从用户审核进入风险信号、关联关系与事件明细 | 先给研判所需事实，再允许下钻原始证据 | 商户风控画像与跨账户网络分析 |

## 3. 设计决策

### 3.1 信息架构

重构后的主路径固定为：

> 案件队列 → 双方主张与事实 → 原始证据/规则 → 判责动作

- 左栏只承担案件选择与状态扫描；
- 中栏默认显示双方主张、事实状态和关键证据；
- 全部证据、规则校验和操作记录使用页签渐进披露；
- 右栏固定展示当前门控结论、规则版本、决定性依据和可执行动作；
- 自动判责仅在确定性内核允许时出现，证据不足或冲突时改为补证/升级复核。

### 3.2 视觉与交互约束

- 页面仅使用一个深色顶栏，主体保持低噪声浅色背景；
- 绿色、橙色、红色只表达状态，不作为大面积装饰；
- 正文与关键证据保持可读字号，弱化说明文案而非缩小核心信息；
- 案件切换支持点击、上一条/下一条按钮和 J/K 快捷键；
- 结论中的证据编号可直接跳转并定位到对应原始证据；
- 焦点态始终可见，窄屏改为单列，判责栏不遮挡内容；
- 系统明确标注“AI 只整理陈述，不参与责任计算”。

### 3.3 原创性边界

本项目只吸收行业共性的流程模式，不复制任何产品的布局尺寸、品牌视觉、文案、图标或字段体系。证衡独有部分包括四态事实模型、证据充分度门控、证明模板版本绑定、证据变异测试和“无法判责”可解释输出。

## 4. 代码级 Harness

### 4.1 领域规则 Harness

使用 Node 原生测试运行 `tests/verdict-engine.test.mjs`，覆盖：

- 4 类金标案件；
- 自动结论的证据引用完整性；
- UNKNOWN 不得被误作反驳事实；
- 决定性证据删除、降质后的安全拒判；
- 高质量冲突证据必须升级人工；
- 同一输入重复 100 次结果完全一致；
- 规则版本追溯；
- 禁止无依据的责任百分比。

### 4.2 组件交互 Harness

使用 Vitest、Testing Library 和 user-event 运行 `tests/workbench.test.tsx`。Testing Library 官方建议优先按照用户可感知的角色和名称查询元素，因此测试不依赖 CSS 类名或实现细节。当前覆盖：

- 默认三段式信息架构；
- 案件切换后门控与动作同步变化；
- 规则细节默认隐藏并可按需展开；
- 证据引用可以跳转定位原始证据；
- J/K 快捷键；
- axe-core 自动无障碍扫描。

### 4.3 静态与构建 Harness

- ESLint + `eslint-plugin-jsx-a11y`：检查 React/TypeScript 规范和常见 JSX 无障碍问题；
- 生产构建：验证可部署产物；
- 真实浏览器检查：桌面、390px 窄屏、键盘流、横向溢出和控制台错误；
- `npm run loop`：按 Harness → Lint → Build 顺序执行，任一阶段失败立即输出 REWORK，否则输出 PROMOTE，并保存机器可读报告。

官方依据：

- Testing Library Queries：https://testing-library.com/docs/queries/about/
- Vitest Component Testing：https://main.vitest.dev/guide/browser/component-testing
- axe-core：https://github.com/dequelabs/axe-core
- WCAG 2.2：https://www.w3.org/TR/WCAG22/

需要注意：自动无障碍扫描不能替代人工键盘、焦点顺序、文案理解和真实任务测试。axe-core 官方也说明自动化只能发现一部分 WCAG 问题，因此自动闸门与浏览器人工验收必须同时保留。

## 5. 当前验收标准

| 维度 | 可执行标准 |
|---|---|
| 清晰性 | 首屏只出现案件选择、研判概览和当前判责，不同时展开所有规则与日志 |
| 效率 | 结论到原始证据不超过 1 次点击；J/K 可连续审核 |
| 安全 | 证据不足或冲突时不展示自动处置动作 |
| 可追溯 | 自动结论绑定规则版本，关键事实具有证据编号 |
| 一致性 | UI 展示结果与确定性引擎输出一致 |
| 可访问性 | 角色查询和 axe 自动扫描通过，键盘焦点可见 |
| 响应式 | 390px 宽度无页面横向溢出、无关键内容丢失 |
| 工程质量 | 领域测试、组件测试、lint、生产构建全部通过 |

## 6. 下一轮真实用户验证

自动测试只能证明实现没有偏离设计约束，不能证明审核员真正好用。建议邀请 5 名未参与开发的同学完成 4 个脱敏案件，记录：首次正确理解门控结论的比例、完成时间、证据定位次数、误点处置次数、对“为什么能判/不能判”的复述正确率。若 5 人中有 2 人以上在同一位置停顿或误解，则先修正信息架构或文案，再扩展新功能。
